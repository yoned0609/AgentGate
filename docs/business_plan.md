# AgentGate 事業企画書 v1.0

> AIエージェント専用 JIT認可基盤
> 作成日: 2026-03-24

---

## 1. エグゼクティブサマリー

AIエージェントが企業のSaaSやデータに自律的にアクセスする時代が到来しつつある。
しかし現状、エージェントにはフルアクセスのAPIキーが渡され、
「何のために、どのデータに触れたか」を監査する仕組みがない。

**AgentGate**は、AIエージェントのリクエストをリアルタイムで解析し、
タスク実行に必要な最小限の権限を**その瞬間だけ (Just-in-Time)** 発行する
バックエンド・プロキシである。

---

## 2. 解決する課題

### 2.1 権限過剰（Over-Privileging）
エージェントに`Full Access`のAPIキーやOAuthトークンを渡すのが現状の標準。
プロンプトインジェクションや挙動異常により、全データが流出するリスクがある。

### 2.2 ガバナンスの欠如
「どのAIが、何の目的（インテント）で、どのデータに触れ、何を返したか」を
記録・監査する標準的な仕組みが存在しない。

### 2.3 導入ハードル
セキュリティ懸念から、企業が社内データへのAIアクセスを禁止するケースが多い。
「安全に使える保証」を提供する基盤がないことが、AI導入の最大のブロッカー。

### 2.4 MCP（Model Context Protocol）の認可空白
AnthropicのMCPはツール/リソースの接続プロトコルを定義するが、
**認可レイヤーを明示的に持たない**。`readOnlyHint`等のアノテーションは
「助言」であり強制力がない。この空白がAgentGateの最大の参入機会。

---

## 3. 解決策（Value Proposition）

### コアコンセプト
AIエージェントとSaaS APIの間に透過プロキシとして挟まり、
**3つの機能**をリアルタイムで提供する：

```
AIエージェント
    ↓ リクエスト
 ┌──────────────────────────────┐
 │        AgentGate             │
 │                              │
 │  1. Intent Analyzer          │  ← リクエストの「意図」を解析
 │     (パターンマッチ + 分類)    │
 │                              │
 │  2. Policy Engine            │  ← ユーザー/組織のポリシーと照合
 │     (RBAC / ABAC / CEL)      │
 │                              │
 │  3. Token Factory            │  ← 最小権限トークンを発行 or
 │     (JIT発行 / プロキシ制御)   │     APIコールをフィルタリング
 │                              │
 │  [Audit Logger]              │  ← 全操作を改ざん不能に記録
 └──────────────────────────────┘
    ↓ 認可済みリクエスト
 SaaS API (Google, Slack, etc.)
```

### 差別化ポイント
- **SDKではなくプロキシ** — 既存コードの変更不要で導入可能
- **MCPネイティブ対応** — MCP ServerとClientの間に挟まるだけ
- **マルチプロバイダ** — Google / Microsoft / Slack等を横断的にカバー

## 4. データフロー（具体例）

```
1. エージェント: 「Aさんの今日の予定を教えて」
2. AgentGate がリクエストをインターセプト
3. Intent Analyzer:
   - パターンマッチ: GET /calendar → "calendar:read" (5ms以下)
   - 対象リソース: Aさんのカレンダー
   - 操作タイプ: 読み取り（非破壊的）
4. Policy Engine:
   - ユーザーポリシー: 「勤務時間内のみ許可」→ OK
   - 組織ポリシー: 「他者のカレンダー閲覧はマネージャー以上」→ 確認
5. Token Factory:
   - Microsoft OBF: Calendars.Read スコープの30秒トークン発行
   - (Googleの場合: プロキシレベルでread-onlyに制限)
6. エージェントがデータ取得
7. トークン自動失効 / Audit Logに記録
```

## 5. 技術的ハードルと対策

### 5.1 トークンダウンスコーピングの現実

調査結果として、**主要SaaSのダウンスコーピング対応は非常に限定的**である：

| プロバイダ | ダウンスコーピング | メカニズム | 制約 |
|-----------|:--:|---------|------|
| Google Cloud (GCS等) | 対応 | CAB (Credential Access Boundaries) | **Workspace API（Calendar/Gmail/Drive）は非対応** |
| Microsoft (Entra ID) | 部分対応 | On-Behalf-Of (OBO) フロー | スコープは事前にアプリ登録で宣言必要 |
| Slack | 非対応 | なし | トークンのスコープはインストール時に固定 |
| Salesforce | 部分対応 | Token Exchange | 主にクロスOrg用途、スコープ縮小ではない |

**対策: ハイブリッドアーキテクチャ**

```
対応プロバイダ → ネイティブ・ダウンスコーピング（OBO, CAB）
非対応プロバイダ → プロキシレベル・フィルタリング（APIファイアウォール方式）
```

プロキシ方式では、各SaaSのAPIスキーマを保持し、
リクエストのHTTPメソッド + エンドポイントで許可/拒否を判定する。
**これが現実的なMVPの主要アプローチ**となる。

### 5.2 インテント解析のレイテンシ

全リクエストにLLM解析を入れると200ms〜2000msの遅延が発生する。

**3段階のフォールバック戦略：**

| レイヤー | 手法 | レイテンシ | カバー率 |
|---------|------|:---------:|:-------:|
| L1 | パターンマッチ（HTTPメソッド + URLパス） | <5ms | 80%+ |
| L2 | 軽量分類モデル（fine-tuned BERT等） | 10-50ms | 15% |
| L3 | LLM解析（曖昧なケースのみ） | 200-500ms | 5% |

エージェントのワークフロー自体がLLM推論で数秒かかるため、
L1/L2で処理できるケースでは実質的な遅延はゼロに等しい。

### 5.3 単一障害点（SPOF）のリスク

プロキシがダウンすると全エージェントが停止する。

**対策：**
- **サイドカーモデル** — エージェントごとにAgentGateプロセスを配置（Envoy的）
- **ポリシーキャッシュ** — ポリシーエンジン到達不能時はキャッシュ済みポリシーで判定
- **Fail-open / Fail-closed** を組織ポリシーで選択可能に
- **将来的にはEdgeデプロイ** — Cloudflare Workers等でグローバル分散

### 5.4 ストリーミング・長時間タスク

エージェントのタスクが数分〜数時間に渡る場合：
- **セッションベース認可** — 開始時に認可し、定期的に再評価
- **チェックポイント認可** — マルチステップの各ステップ境界で認可チェック
- **トークンリフレッシュプロキシ** — AgentGateが透過的にリフレッシュを代行

## 7. 競合分析

| プロダクト | アプローチ | AgentGateとの差異 |
|-----------|-----------|-----------------|
| **Pangea** | セキュリティAPI群（SDK組込） | SDKベース＝コード変更必須。AgentGateはプロキシ＝透過的 |
| **Indent** | 人間向けJITアクセス | 人間の承認フロー前提。AIエージェントの自律的判定に非対応 |
| **ConductorOne / Opal** | ID Governance | 人間のアクセス管理が主軸。AIエージェント特化ではない |
| **Permit.io / Cerbos** | ポリシーエンジン | 認可判定エンジンのみ。トークン発行・プロキシ機能なし |
| **Lakera** | AIファイアウォール | プロンプトインジェクション防御が主軸。API認可ではない |

**AgentGateの独自ポジション：**
「インテント解析 + JITトークン発行 + 監査ログ」を
**プロキシとして透過的に提供**するプロダクトは現時点で存在しない。

**最大のリスク：**
Google / Microsoft / Anthropicがプラットフォーム機能として
同等の認可レイヤーを内製する可能性。
→ **マルチプロバイダ横断**がこのリスクへの回答。単一プラットフォームには作れない。

## 11. ContextFlowとのシナジー

AgentGateはContextFlowの**セキュリティレイヤー**として統合可能：

```
ユーザー → ContextFlow → AgentGate → Google Calendar API
                                    → Supabase Storage
                                    → OpenAI API
```

**具体的なメリット:**
- ContextFlowのカレンダー同期に「勤務時間内のみ」「自分の予定のみ」等の制限を適用
- ファイルアクセスの監査証跡をAgentGateで一元管理
- ContextFlowのEnterprise版セールスで「AgentGate搭載」をセキュリティ訴求に活用
- AgentGateの事例・ドッグフーディング先としてContextFlowを利用

**ただし事業としては独立:**
- 別リポジトリ、別ドメイン、別ブランド
- ContextFlowに依存しない汎用プロダクト
- ContextFlowはAgentGateの「最初の顧客」

## 12. リスクと対策

| リスク | 影響度 | 対策 |
|-------|:-----:|------|
| プラットフォーマーが同等機能を内製 | 高 | マルチプロバイダ横断を差別化軸に。単一プラットフォームには作れない価値 |
| トークンダウンスコーピング非対応のSaaSが多い | 中 | プロキシ方式を主軸とし、ネイティブ対応は最適化として位置付け |
| エージェント市場の成長が想定より遅い | 中 | 人間向けJITアクセスにもピボット可能（Indent的ポジション） |
| セキュリティ製品としての信頼獲得に時間がかかる | 中 | OSS化で透明性確保 + ContextFlowでの自社利用実績を提示 |
| 個人開発のリソース制約 | 高 | Phase 1はGoogle Calendar 1本に集中。ContextFlowの技術資産を最大限流用 |
